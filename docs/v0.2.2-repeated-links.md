# Third full run (0.2.2): PDF links that two governments both post

**Added 2026-10-19.** A dated note. Nothing in [results/v0.2.2/](../results/v0.2.2/) or in the third full run's section of the README was changed; this page says what was found, and gives every count exactly as the script printed it.

## What was found

When the lang-census's public rows were about to go into this repository, a test of ours assumed that every row has its own PDF link, and 4 of its 4,339 rows did not ([docs/lang-census-results.md](lang-census-results.md), "Added 2026-10-19: repeated links"). The reason is in the crawl: `census.py` 0.2.2's `crawl_site` drops a PDF link that it meets twice on one site (`dict.fromkeys` over that site's links) but keeps no list across sites, so a PDF that two governments both link to is read once for each of them and is a row for each. That is how the census counts, by design: one row per PDF each site's crawl read, so that per-site figures and the within-site comparison are about what each site publishes.

The third full run (0.2.2) uses the same crawl, so the same applies to it. Its per-PDF records are not published (their file names and software strings were not checked for personal names), so the counts below were taken from the job's own output and cannot be recomputed from this repository. `repeat_links.py` is the script that counted them; it is standard library only, prints counts and shares and nothing else (no URL, hash or site id), and `test_repeat_links.py` checks it on made-up rows. Anyone who runs the census gets a `pdfs.jsonl` to run it on.

## Reading

- **Third full run:** 3 of the 5,412 PDFs read (0.06%) are a link that two governments both post, so each is counted for both. No link was counted twice for one site, which is what the crawl code guarantees. All three repeated PDFs are tagged, marked, have a document language and pass all four basics, so with each link counted once every share falls a little: tagged 3,274 of 5,412 (60.50%) against 3,271 of 5,409 (60.47%); marked 2,996 (55.36%) against 2,993 (55.33%); document language set 3,062 (56.58%) against 3,059 (56.55%); all four basics 1,191 (22.01%) against 1,188 (21.96%). At one decimal, as the results page prints them, tagged, document language and all four basics are the same either way; the Marked line in `results/v0.2.2/results.md` would print 55.3% instead of 55.4%.
- **lang-census:** 4 of the 4,339 rows repeat a link (3 links: two posted by two sites each, one by three), all from different sites. None of the 65 non-English rows is among them, so no scored verdict changes; `test_results_lang.py` checks this and recomputes every verdict with each link counted once. `/Lang` present: 2,795 of 4,339 (64.42%) against 2,791 of 4,335 (64.38%).
- **No published number is changed.** The figures on the README and in `results/v0.2.2/` count per site, as the census defines them. This page is the record that the definition counts a shared PDF once per site that posts it, and of how little that matters here.

## Limits

- The counts come from the job's private per-PDF records, not from files in this repository, so `test_results_v022.py` does not recompute them. The script and its test are published so the counts can be re-made from any census run.
- Links are compared as exact strings after the census's own normalisation, so one PDF posted at two different addresses counts as two links, and the repeat counts are a floor.
- The effect is tiny for this cohort's own documents. A crawl that reads many shared documents (state forms, federal notices that many governments post) would see more of it, and a future census version could report distinct links alongside per-site rows; 0.2.2 is not being changed for that.
