# title2-pdf-census

**How accessible are the PDFs that large US local governments publish, six months before their ADA Title II deadline?**

The U.S. Department of Justice's ADA Title II rule (published 2024-04-24; deadlines moved by one year in April 2026) requires state and local governments serving **50,000 people or more** to make their web content, including PDF documents, meet **WCAG 2.1 AA by 2027-04-26**. Smaller governments and special districts have until 2028-04-26.

This tool takes that cohort and measures the basics:

1. **Cohort:** US cities, counties, consolidated city-counties and towns with a population of 50,000+ and an official website on Wikidata (one row per website).
2. **Crawl, public pages only:** for each site it reads robots.txt, the home page, up to 8 pages linked from it, and up to 8 PDFs linked from those pages. Requests to any one site are made one at a time with a 1-second pause, and robots.txt is honoured. The User-Agent names Munim, Inc. and gives an email address.
3. **Checks on each PDF** (machine-checkable structure that screen readers rely on):
   - **tagged**: has a structure tree (`/StructTreeRoot`)
   - **language**: the document language (`/Lang`) is set (whether it matches the text is a separate test, lang-census, below)
   - **title**: a title is set in the metadata
   - **image only**: no extractable text on the first two pages (likely a scan without OCR)
   - **all four basics**: tagged, language and title set, and not image only
   - figures in the structure tree, and how many have alt text
   - the creation date, so **PDFs made after the rule can be compared with older ones**, overall and within the same site
   - the software that made it (Word, Acrobat, a scanner, print-to-PDF, ...)
4. **One check on each home page** (new in 0.2.0): does it link to a page about accessibility or the ADA? A link counts if its URL path contains "accessib" or "section-508", or its text contains "accessib", "Section 508" or "ADA" in capitals (not "ADA County"). This is a rough signal of whether residents can find an accessibility statement or a way to report a barrier; the rule itself does not require one.

## What it is not

Passing these checks is **necessary but not sufficient** for an accessible PDF: correct reading order, meaningful alt text, table headers and colour contrast need a person or deeper tools. Nothing here is a WCAG conformance judgment about any government, and no result says anyone is out of compliance. The sample is the PDFs reachable within two clicks of each home page, so it over-represents current documents such as agendas, minutes and notices. The home-page link check misses statements linked only from inner pages or footers rendered by script, and counts some links that are about physical access.

The tool stores **structural facts only**: no document text, no metadata titles, no personal data.

## Prior work

- Allyant's *PDF Accessibility Index 2025-2026* (March 2026) scanned 644,854 PDFs on 770+ websites across sectors and reported 97.12% of government PDFs inaccessible. It is a vendor report with proprietary data and no per-government or local-government breakdown.
- Accessible Compliance Group's *2026 State of Government Website Accessibility* scanned 15,481 government websites but excluded PDFs.
- The WebAIM Million tests home pages, not documents.

As far as we could find, this is the first **open, reproducible, per-government** measurement of PDF basics for the governments facing the 2027 deadline, and the first to ask whether **documents made since the rule** are better than older ones.

## Use

```
pip install "pypdf[crypto]"
python census.py cohort --out cohort.csv
python census.py crawl --cohort cohort.csv --sites-out sites.jsonl --pdfs-out pdfs.jsonl
python census.py summarize --sites sites.jsonl --pdfs pdfs.jsonl --out-dir .
python -m unittest -v
```

`summarize` writes `summary.json`, `results.md` (shares with 95% Wilson intervals) and `sites.csv` (one row per government).

**Records for a later re-crawl (since 0.2.3).** Each crawl also writes what a later crawl needs to say why it missed a file, by address hash only (the SHA-256 of the URL, as the published rows use): each site record lists every PDF link found (`pdf_links_sha256`), the ranked candidates and how far the crawl got through them (`candidates_sha256`, `candidates_looked_at`, `stopped`) and each inner page tried (`pages`: hash, status and number of PDF links); each PDF record adds the page its link was found on (`found_on`), its rank (`candidate_rank`) and, for a fetch that got no response, a coarse cause (`no_response`: timeout, dns, tls, refused, reset or other, never the error text). `miss_reason()` reads them. `python census.py retry --pdfs pdfs.jsonl --out retry.jsonl --wait-minutes 60` fetches once more, after the wait, every PDF that got no response, with the same manners (robots.txt honoured, a pause between requests); its records go to their own file and never change the crawl's records or `summarize`. The pages and PDFs sampled, the requests made and every field 0.2.2 wrote are unchanged: `test_census_023.py` runs 0.2.2's crawl (kept as `fixtures/census_0_2_2.py`) and 0.2.3's on the same synthetic site with seven settings and checks that they make the very same requests in the same order and write the same values.

## Accessibility statements: what the linked pages promise (2026)

The Title II rule adopts WCAG 2.1 Level AA. A pre-registered follow-up, [results/a11y-pages](results/a11y-pages/A11Y-PAGES-RESULT.md), read the accessibility page linked from each home page of the 50,000+ cohort in October and November 2026: of 1,657 governments, 1,195 home pages and 808 accessibility pages could be read. 508 of those pages name a WCAG version; for 283 of them (55.7%) the highest is WCAG 2.0, for 195 WCAG 2.1 and for 30 WCAG 2.2. 280 of the 808 carry the same stock sentence ("We work to comply with Section 508 as well as WCAG 2.0 A and AA ..."; counted after the crawl, not pre-registered). 179 name Title II. Of the 17 that give a compliance date, 12 give only April 24, 2026, the date the interim final rule of April 20, 2026 moved to April 26, 2027. Two of the four graded predictions held; a fifth had too few dated pages to grade. A statement's wording is not a WCAG conformance judgment, and the rule does not require a statement.

**Check one statement (statement_check).** [STATEMENT-CHECK.md](STATEMENT-CHECK.md) explains `statement_check.py`, a free check of one accessibility page by the same rules: which WCAG versions it names, whether it carries the stock sentence, and whether it gives a compliance date the interim final rule replaced (use `--small` for governments of under 50,000 and special districts, whose date is now April 26, 2028). It reads only what the page says, not whether the site meets WCAG, and it is not legal advice.

```
python statement_check.py --find https://www.example.gov
python statement_check.py https://www.example.gov/accessibility --small
```

**Pre-registered next steps.** [results/statement-reread](results/statement-reread/PREREG.md) reads the same 808 pages again in January-February and May-June 2027, before and after the April 26, 2027 date, to see whether they change.

**Smaller governments (result, 2026-11-02).** A pre-registered follow-up, [results/small-pages](results/small-pages/SMALL-PAGES-RESULT.md) ([plan](results/small-pages/PREREG.md)), read the accessibility pages of 2,500 sampled US cities, counties and towns of 10,000 to 49,999 people: 1,942 home pages and 1,042 accessibility pages could be read. Of the 809 pages naming a WCAG version, 638 (78.9%) name only WCAG 2.0, against 55.7% in the 50,000+ cohort; 698 of the 1,042 carry the same stock sentence. Only 94 name Title II and only 3 give any compliance date. 1,053 of the 1,942 home pages (54.2%) link to an accessibility or ADA page. All four graded predictions held; the fifth, on dates, had too few dated pages to grade.

**Is the page an unfinished template? (statement_check2).** [STATEMENT-CHECK2.md](STATEMENT-CHECK2.md) explains `statement_check2.py`, which reports everything statement_check does and adds two findings: `template-placeholder`, for a page that still carries vendor template text never filled in (`YOURMUNICIPALITY`, the note "only meant as a template", a `NAME / TITLE / EMAIL / PHONE` block, or a bracketed placeholder such as `[URL OF WEBSITE]`), and `stock-no-wcag`, for the stock sentence with the word WCAG missing, so that the page names no standard at all. Its placeholder rules are those of the pre-registered [results/template-pages](results/template-pages/PREREG.md) study, which reads the 1,850 accessibility pages of both cohorts again to count how many are still an unedited template. A placeholder says nothing about whether a website is accessible; it says the statement was never finished.

**Unfinished templates (result, 2026-11-06).** The pre-registered [template-pages](results/template-pages/TEMPLATE-PAGES-RESULT.md) study read the accessibility pages of both cohorts again: of 1,843 pages read, 29 are still a vendor's statement template with its placeholders unfilled (the government's name given as "YOURMUNICIPALITY", the note "only meant as a template", or a NAME / TITLE / EMAIL / PHONE contact block). That is 25 of 1,038 pages of governments of 10,000 to 49,999 people (2.41%) and 4 of 805 pages of governments of 50,000 or more (0.50%). 28 of the 29 are on CivicPlus sites, and 24 of them had not been seen before the test. All five predictions held. A placeholder says nothing about whether a website is accessible; it says the statement was never finished.

**School districts (plan, 2026-11-06).** [results/district-pages](results/district-pages/PREREG.md) pre-registers the same reading for US public school districts, which are Title II entities too: 2,500 districts sampled from the NCES Common Core of Data 2024-25 directory matched to the Census Bureau's SAIPE 2024 populations (800 of 50,000 or more people, 1,700 under 50,000), with six predictions fixed before any district page is read. No published study we found counts what school districts' accessibility statements say.

## Check one website (site_check)

`site_check.py` runs the same checks on one website, or on a list of PDF links, and writes a plain-language report: which PDFs pass the four basics, and for each one that fails, what to fix (for example, the Word export option that adds tags, or where to set a title and a language). It is meant for the people who publish the PDFs: a city clerk, a web team or a consultant checking their own site before the deadline.

```
python site_check.py https://www.example.gov/ --md report.md --json report.json
python site_check.py --pdf https://www.example.gov/docs/agenda.pdf --md report.md
```

The same manners apply: public pages only, robots.txt honoured, a pause between requests. The same limits apply too: machine checks of four basics, not a WCAG conformance judgment or legal advice. It finds links with the census's own code, so the 0.2.2 fix below (links on pages that set `<base href>`) applies to it as well. Unlike the census, it does not pick pages at random: since 0.1.1 it reads pages that look like document lists first (Documents, Agendas, Forms, Library, CivicPlus's DocumentCenter and the like, by link text or address), follows such links one level further, and stops once it has twice as many PDF links as PDFs to check. Its first version sampled pages as the census does and found no PDF at all on section508.gov or ada.gov. Since 0.1.2, once half its pages are read with no PDF link, it reads the site's other pages first, and since 0.1.3 it reads up to 16 pages by default, so it falls back only after 8 document-like pages (see the tests below). If it finds no PDF on your site, give PDF links directly or raise `--pages` (up to 30 in the Actor). The `.actor/` folder packages it as an [Apify](https://apify.com) Actor (`actor_main.py`), so it can also run without installing anything. Smoke runs on the Actor's example sites: [docs/smoke-tests.md](docs/smoke-tests.md).

**Does the document language match the text? (since 0.2.0)** For each readable PDF, site_check also reads the text of the first 5 pages and compares its language with the declared `/Lang`, with lang-census's own rules (below): `langmatch.py` holds lang.py 0.1.1's detection code unchanged, and `test_langmatch.py` checks that it still is. If the text is clearly in one language and the PDF declares another, or declares none, the report says which language to set and where. When parts of the file are already marked with the text's language and only the document language is wrong (since 0.2.1), it leads with the fix in Acrobat's document properties and says that choosing Word's proofing language again may not help, because the text already carries it ([docs/lang-word-note.md](docs/lang-word-note.md)); otherwise it gives both Acrobat's document properties and Word's proofing language before saving as PDF again. A mismatch is listed under "Also worth fixing", not as a fifth failed basic, so the four basics and their counts are the same as before. The report adds one line counting the PDFs whose text language was clear and how many of those declare a different language or none; the JSON adds a `lang_check` record per PDF and a summary; Actor dataset rows add `declared_lang`, `text_lang` and `lang_matches_text`. The check needs py3langid and langdetect (`pip install py3langid==0.4.0 langdetect==1.0.9`, the versions lang-census ran with; the Actor installs them from `requirements-actor.txt`). Without them the report says the check was not run, `--no-lang-check` turns it off, and a language check that fails on a PDF never costs it its four basics. It gives no verdict on PDFs with too little text the two detectors agree on, or with no language holding 80% of it.

## Test: how much of a "tagged" PDF can a screen reader reach? (tagtree)

The census counts a PDF as tagged if it has a structure tree. `tagtree/tagtree.py` asks how much of the text is actually in that tree: it walks the tree from its root, as a screen reader in tag order does, and sorts every character on the first 3 pages into reachable, **untagged** (not in any marked content and not an artifact) or **dangling** (marked content the walk never reaches). Four predictions were written down before it ran ([docs/tagtree-reach-prereg.md](docs/tagtree-reach-prereg.md)), plus two outside checks of the code. Results, scored prediction by prediction: [docs/tagtree-reach-results.md](docs/tagtree-reach-results.md); files in [results/tagtree-v1/](results/tagtree-v1/); `test_results_tagtree.py` recomputes every number quoted here.

- **Two of the four predictions held.** On 753 tagged PDFs from 308 local-government sites, 49 (6.5%) leave 5% or more of the text on their first 3 pages unreachable from the tree, fewer than the 10% we predicted. Word output is leaky less often than the rest (3.6% against 8.2%), but by 4.7 points, not the 10 predicted. 32 PDFs (4.2%) have a page of text where a screen reader in tag order reaches nothing, above the 2% predicted. Most trees follow the order of the content stream, as predicted.
- **Tagged in name only:** 9 of the 753 have a structure tree with at most one element, and all 9 are leaky, so the census's "tagged" share slightly overstates usable tags. 23 PDFs have dangling text.
- **Outside checks:** on the veraPDF PDF/UA-1 corpus, tagtree found no unreachable text in any of the 130 pass files with text; of the two fail files for "content shall be tagged or an artifact", it found the one whose untagged content is text and missed the one whose untagged content is an image, which tagtree does not measure ([docs/tagtree-verapdf-results.md](docs/tagtree-verapdf-results.md)). On the file from veraPDF issue #1629 it flagged exactly the three orphaned marked-content IDs the reporter named ([docs/tagtree-orphans-results.md](docs/tagtree-orphans-results.md)).
- **Cross-check with a second, independent reader:** a re-crawl with the same seed read 759 eligible PDFs with tagtree and with a separate pypdf reader. All five pre-registered checks held, and on 757 of the 759 the two agree on every check ([docs/tagtree-xcheck-results.md](docs/tagtree-xcheck-results.md); files in [results/xcheck-v1/](results/xcheck-v1/); `test_results_xcheck.py` recomputes its numbers). The two exceptions are Word PDFs from the first run's sample, where tagtree finds almost no tree and the pypdf reader a full one, and they hold 13,259 of the first run's 24,047 dangling characters.
- **Correction (2026-10-18):** two diagnostic jobs ([results/diag-v1/](results/diag-v1/), [results/diag-v2/](results/diag-v2/)) showed that tagtree misread those two files. In them, the cross-reference index of most objects stored in compressed object streams disagrees with the stream's own list of object numbers; pdfminer.six, which tagtree uses, trusts the index and returns neighbouring objects, while pypdf and qpdf look the number up. Read correctly, both files are fully reachable, so the first run has 47 leaky PDFs, not 49 (6.2%, not 6.5%); Word 2.9% against 8.2% (5.4 points); 31 with a shell page; 8 with at most one element; 21 with dangling text; and 3.5% of its characters unreachable, not 4.1%. None of the four verdicts changes; the figures above are as first published, and both results pages give the corrected ones next to them. tagtree 0.1.1 (released 2026-10-18) finds object-stream members by number; reading both files again, it gives exactly these corrected records, and with `--xref-index` exactly the first-published ones ([results/tagtree-011/](results/tagtree-011/)).
- **How common are such files? (objstm-census, 2026-10-18):** a pre-registered re-run of the same seeded crawl with tagtree 0.1.1 found object streams in 715 of 775 eligible tagged PDFs, and indexes that disagree with the stream's header in only 2 of them (0.3%): the same two Word files, with the same bytes. Only those two records change when objects are found by index, as 0.1.0 did; 135 other Word for Microsoft 365 files have no such index. All three predictions held ([docs/objstm-census-results.md](docs/objstm-census-results.md); files in [results/objstm-v1/](results/objstm-v1/); `test_results_objstm.py` recomputes its numbers).
- **Limits:** machine checks of the first 3 pages; text wrongly marked as an artifact is not detected; invisible text such as an OCR layer is counted; the cross-check compares two readers written by the same team, so it tests the parsing and the walk, not the definitions.

## Test: does a PDF's declared language match its text? (lang-census)

The census only asks whether `/Lang` is set. Screen readers use it to pick a voice and pronunciation rules, so a Spanish notice whose `/Lang` says English is read with English rules. `results/lang-v1/lang.py` reads the text of the first 5 pages with two independent language detectors (py3langid and langdetect, which must agree), and compares the text's language with the catalog `/Lang`, the structure elements' `/Lang` and inline marked-content `/Lang`. Four predictions and a detector-agreement check were written down before it ran ([docs/lang-census-prereg.md](docs/lang-census-prereg.md)), and a note on how the check could fail was published while the job ran, before any output was seen ([docs/lang-census-note-before-results.md](docs/lang-census-note-before-results.md)). As far as we could find, no earlier study measures whether PDF `/Lang` values match the text; the closest work measures missing declarations, or mismatches on web pages. Results, scored prediction by prediction: [docs/lang-census-results.md](docs/lang-census-results.md); files in [results/lang-v1/](results/lang-v1/) (the 4,339 public rows are in numbered parts under 2 MB each, `lang-public-1.jsonl` and `lang-public-2.jsonl`; `split-report.json` gives their sizes and SHA-256 and those of the job's original file); `test_results_lang.py` recomputes every number quoted here from them. site_check runs the same check on one website since 0.2.0 (above).

- **All four predictions and the agreement check held.** On a fresh crawl of the same cohort, 4,339 PDFs with text were checked; 2,813 are English and 65, from 46 sites, are in another language (54 of them Spanish). Of those 65, 57 (87.7%; site-resampled 95% interval 75.7% to 97.0%) have a `/Lang` that is missing (19) or names another language (38, all of them English). Of the 38 declared English, 16 (42.1%) name the real language on a structure element or in marked content, so a reader that honours local tags would get them right; 22 give it no clue.
- **The other direction is rare:** 3 of 2,813 English PDFs declare another language, and 3 of 2,795 `/Lang` values are not BCP 47-shaped (all `EN_US`).
- **Word-made files (exploratory, added 2026-10-19):** of the 16 that declare English while naming the real language inside, 11 are Word output: in 11 of Word's 13 English-declared non-English PDFs parts of the file already carry the real language, against 2 of 14 for Adobe output. This breakdown was chosen after the results were public, so it is a pattern worth testing, not a scored finding ([docs/lang-word-note.md](docs/lang-word-note.md); `test_lang_word_note.py` recomputes its numbers). It is why site_check 0.2.1 leads with the Acrobat fix for such files.
- **Confirmatory test of the Word pattern (wordsig, pre-registered, scored 2026-10-19): inconclusive.** On 1,616 PDFs from 367 Canadian municipal websites listed on Wikidata, 60 declare a language other than their text's: 6 Word-made and 46 Adobe-made, short of the pre-registered minimum of 8 of each, so the main prediction was not scored and nothing is claimed ([docs/wordsig-prereg.md](docs/wordsig-prereg.md), [docs/wordsig-results.md](docs/wordsig-results.md); `test_wordsig_results.py` re-scores the public rows). The Word pattern stays exploratory. site_check's advice for any one file does not depend on it: it leads with the Acrobat fix only when that file's parts already carry the text's language.
- **French PDFs in Quebec and elsewhere (qcfr, pre-registered, scored 2026-10-19): inconclusive, too few.** Of the wordsig crawl's French-text PDFs, 7 of 7 outside Quebec (6 sites) and 186 of 433 in Quebec (88 sites) have a `/Lang` that is missing, unusable or names another language. No new crawl was made ([docs/qcfr-prereg.md](docs/qcfr-prereg.md), [docs/qcfr-results.md](docs/qcfr-results.md); `test_qcfr_results.py` runs the test again from the public site table).
- **Limits:** text from the first 5 pages only; about a third of the PDFs got no text language (too little text the two detectors agreed on); L1 and L2 rest on 65 and 38 files; no screen reader was tested.

## Test: does reading document pages first find more PDFs?

A paired test of site_check 0.1.1 against the census's random page sampling, with five predictions written down before it ran ([docs/doc-first-prereg.md](docs/doc-first-prereg.md)). Results, scored prediction by prediction: [docs/doc-first-results.md](docs/doc-first-results.md); files in [results/doc-first/](results/doc-first/); code in `doc_first_reach.py`; `test_doc_first_reach.py` recomputes every number quoted here.

- **Four of the five predictions held.** On the local-government sites where the second full run read pages but found no PDF link, reading document-like pages first found one on 60 of 127 sites, against 2 for random pages (exact McNemar p = 1.1e-16).
- **One failed.** On sites where random pages already found PDFs, site_check 0.1.1 reached a readable PDF less often (88 of 97 against 92 of 97), 4.1 points worse, more than the 2 points the pre-registration allowed. At most of the sites it missed, every page it read was document-like and none linked a PDF.
- **What changed:** site_check 0.1.2 falls back to the other pages once half its pages turn up no PDF link. Its own test is below.
- **Correction (found by the third test):** "2 for random pages" overstates the gain. The census's sampler is seeded by the site's address, so the random-pages arm re-read the same 8 pages on which the census had found no PDF link, which is how these sites were chosen. Its near-zero score was built into the design. See the third test below.

## Test: does site_check 0.1.2's fallback keep the gain and win back the loss?

Three arms on the same sites the same day (random pages, 0.1.1 and 0.1.2, 8 pages each), with six predictions written down before it ran ([docs/doc-first-v2-prereg.md](docs/doc-first-v2-prereg.md)). Results, scored prediction by prediction: [docs/doc-first-v2-results.md](docs/doc-first-v2-results.md); files in [results/doc-first-v2/](results/doc-first-v2/); code in `doc_first_reach_v2.py`; `test_doc_first_reach_v2.py` recomputes every number quoted here.

- **Five of the six predictions held.** On 200 control sites the first test did not use, 0.1.2 reached a readable PDF on 175 of 193 sites, against 177 for random pages and 170 for 0.1.1: the fallback won back what 0.1.1 lost there.
- **One failed.** On the hard sites, where random pages had found no PDF link, 0.1.2 found one on 46 of 125 sites, against 59 for 0.1.1 and 2 for random pages: 10.4 points below 0.1.1, more than the 5 points allowed. With 8 pages it falls back after 4 document-like pages, and at 13 of the 14 sites it lost, 0.1.1 had read 5 or more.
- **Correction:** the same flaw applies here: the 2 for random pages on the hard sites were the census's own 8 pages read again. The comparisons between 0.1.1 and 0.1.2 are not affected.

## Test: with 16 pages, does site_check 0.1.2 keep what 0.1.1 found and match random pages?

Three arms on the same sites the same day (random pages with 16 pages, 0.1.1 with 8, 0.1.2 with 16), with six predictions written down before it ran ([docs/doc-first-v3-prereg.md](docs/doc-first-v3-prereg.md)). Results, scored prediction by prediction: [docs/doc-first-v3-results.md](docs/doc-first-v3-results.md); files in [results/doc-first-v3/](results/doc-first-v3/); code in `doc_first_reach_v3.py`; `test_doc_first_reach_v3.py` recomputes every number quoted here.

- **Five of the six held.** On 200 control sites neither earlier test used, 0.1.2 with 16 pages reached a readable PDF on 180 of 195 control sites, exactly as many as 16 random pages, while reading 849 inner pages against 3025. On the hard sites it found a PDF link on 70 of 122, against 56 for 0.1.1 and 58 for random pages, so 16 pages wins back what 8 pages lost.
- **One failed, and it exposed a flaw in the first two tests.** The prediction that 0.1.2 would beat random pages on the hard sites at p < 0.01 failed: 70 against 58 sites, with 24 against 12 on the discordant pairs (exact McNemar p = 0.065). With 16 pages, random pages read 8 pages the census had not read and found PDF links on about half the hard sites, where with 8 pages they had found them on 2. The census's sample is reproducible (seeded by the site's address), and the hard sites were chosen because its 8 pages found nothing, so re-reading those 8 pages could not do better.
- **What changed:** site_check 0.1.3 reads 16 pages by default. Its advantage over random pages is mainly cost (about a quarter as many pages read where PDFs are easy to find) and somewhat more reach on hard sites, not the "60 against 2" of the first test.

## Test: did new PDFs change around the 2026 Title II extension? (four follow-ups)

On 2026-04-20, four days before the original date, the Justice Department moved the compliance date for governments of 50,000+ from 2026-04-24 to 2027-04-26. Four follow-ups split the third full run's PDFs (below) by the date each file was created, around that day. For each one, the predictions and the tested script were committed before the counts were read, and a results page grades the predictions one by one. Code: `deadline_split.py`, `site_split.py`, `title_mix.py` and `title_pairs.py`, each tested on synthetic rows by its own `test_*.py`. The row file they read is not published because its rows name sites; `census.py` regenerates such a file. One-line summaries are also in [docs/measured.md](docs/measured.md).

- **Deadline split: 2 of 6 predictions held** ([docs/deadline-split-prereg.md](docs/deadline-split-prereg.md), [docs/deadline-split-results.md](docs/deadline-split-results.md)). Pooled over the 12 months on each side, PDFs created after the extension were tagged as often as before (67.2% against 67.3%). In the 3 months just before it 74.4% were tagged, and in the 3 months after 66.7%; the same months a year earlier moved the other way. The share with a title in the metadata fell from 45.1% to 39.0%.
- **Site split: 4 of 6 held** ([docs/site-split-prereg.md](docs/site-split-prereg.md), [docs/site-split-results.md](docs/site-split-results.md)). With one vote per government, the 3-month tagging drop is 5.5 points (95% CI -12.8 to +1.9). Among the 102 governments with files in both windows, 25 went up and 20 down (sign test p = 0.55): no decline within the same governments.
- **Title mix: 6 of 6 held** ([docs/title-mix-prereg.md](docs/title-mix-prereg.md), [docs/title-mix-results.md](docs/title-mix-results.md)). Of the 6.1-point fall in titles, 5.3 points is within the same software groups (Word, Acrobat and so on) and 0.8 a change in which software made the files.
- **Title pairs: 5 of 6 held** ([docs/title-pairs-prereg.md](docs/title-pairs-prereg.md), [docs/title-pairs-results.md](docs/title-pairs-results.md)). Within the 329 governments with files on both sides, the average title share fell 3.7 points (95% interval -9.5 to +2.1; 93 up, 103 down, sign test p = 0.52). That is past the -3 point line set in advance, so that prediction failed. In the 3 months either side of the extension, the 102 governments with files on both sides show no drop (+0.8 points).
- **Read together:** both drops look mostly like a change in which governments posted in each window, not governments changing their own practice. That reading is untested, not a finding.
- **Limits:** a file's creation date is not when it went online, files that were replaced or taken down are missing from the older windows, metadata dates can be wrong, and the extension came four days before the original date, so none of this shows cause. Machine checks only; no government is named.

## Test: does a re-crawl see the same files? (panel retest and miss reasons)

A same-file panel, measuring the very same PDFs again in 2027, first needs to know how many files a re-crawl misses when nothing has changed, and how often the checks change on the same file. The second (0.2.1) and third (0.2.2) full runs crawled the same sites about six hours apart on 2026-10-16, so two pre-registered checks match their files by government and a hash of each address (no address is stored). For each one, the predictions and the tested script were committed before the script was run on the data, and a results page grades the predictions one by one. Code: `panel_retest.py` and `miss_reasons.py`, each tested on synthetic rows by its own `test_*.py`. The row files they read are not published because their rows name sites; `census.py` regenerates such a file. One-line summaries are also in [docs/measured.md](docs/measured.md).

- **Panel retest: 6 of 6 predictions held** ([docs/panel-retest-prereg.md](docs/panel-retest-prereg.md), [docs/panel-retest-results.md](docs/panel-retest-results.md)). The later crawl read again 91.3% of the 5,285 PDFs the earlier one read (94.1% on the 892 sites read in both). On the 4,826 files read twice, the five checks agreed on all but 3 (99.94%) and the byte count on all but 7. Within sites, failing files were read again slightly less often than passing ones (mean -1.8 points; 70 sites down, 29 up, sign test p = 0.00005).
- **Miss reasons: 3 of 4 held** ([docs/miss-reasons-prereg.md](docs/miss-reasons-prereg.md), [docs/miss-reasons-results.md](docs/miss-reasons-results.md)). That within-site gap sits mostly in files that were tried again and got no response (a timeout, or a DNS, TLS or connection error): failing files ended that way 1.4 points more often (42 sites up, 11 down, sign test p = 0.00002), while files with no row at all in the second crawl added 0.4 points (31 up, 18 down, p = 0.085). File size does not explain it, so the size prediction failed: comparing files of similar size leaves the gap at -1.12 points, against -1.08 without. It is not a `<base href>` effect either.
- **Floors for a 2027 panel:** files not read again although nothing changed: 8.7% of all files, 5.9% on sites read in both crawls; same file, different check result: 0.06%. A finding that failing PDFs were taken down more often has to beat these, compare within sites, retry files that got no response, and record why each file was missed.
- **Limits:** six hours is short; the `<base href>` fix between the two crawls adds misses on the sites it affects; the crawls ran on different machines; machine checks only; no government is named.
